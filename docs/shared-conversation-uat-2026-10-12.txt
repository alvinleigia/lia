SHARED CONVERSATION FIX AND UAT - 12 October 2026

Scope: shared knowledge retrieval and conversational-task handling for hotel,
service and appointment enquiries. No hotel-specific extraction code was added.

CAUSES AND CORRECTIONS
- Vector-only search excluded explicit pool facts below the similarity cutoff.
  Added project-scoped lexical retrieval alongside semantic retrieval.
- An internal four-excerpt cap hid the sixth-ranked alternative rate plan.
  Honour the configured excerpt count, within the existing 6,000-character budget.
- Mixed field updates and questions followed the field-only branch. Validate and
  retain supplied fields, answer the question using refreshed state, then resume.
- Canonical date ranges were missing from model context. Preserve both endpoints.
- Knowledge answers could re-extract fields instead of answering. Enforce stage
  boundaries through validation, with the existing bounded repair path.
- Explicit hour-only times such as "9 am" were rejected. Normalize these while
  continuing to reject ambiguous bare hours and invalid clock values.
- Keep procedural confirmation questions on the task path. When the last required
  detail includes an FAQ, answer it and prepare the required operation review.
  Preparation does not execute a booking.
- Model instructions retain material offer restrictions and prohibit reusing an
  old quote after its dates/occupants change or exposing internal excerpt IDs.
- Live retest exposed a redundant recommendation of the already active task.
  Normalize confident same-task recommendations to a no-op instead of triggering
  repair/fallback. Different targets, uncertainty and unauthorized proposals remain
  subject to validation. The real hotel extraction then passed in one model call.
- Re-evaluate required-field order after a mixed correction so newly required
  dependencies (such as child ages) precede the old pending contact question.
  Pure FAQ interruptions still resume the exact pending field.
- The active-task knowledge stage now uses a restricted provider schema as well
  as server validation: no field edits, task switches or operation proposals.
- A live changed-price question exhausted the 900-token output cap in reasoning.
  Detect truncation, retain its usage and try the configured fallback directly;
  do not repeat the same capped attempt or increase the configured token limit.
- Preserve explicit completion proposals rather than normalizing them into FAQ
  interruptions. Allow a completed outcome when the validated fields are already
  complete and the visitor explicitly requests submission; server gates still apply.
- Ignore a stale requested-field pointer once that field is valid/confirmed.
  This prevents a later submission sentence from overwriting a collected name.
  Render completed task wording from the applied server outcome, rather than a
  model proposal which might still ask for confirmation.
